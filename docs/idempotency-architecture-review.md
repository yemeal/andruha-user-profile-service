# User Profile: результат рефакторинга идемпотентности

Дата: 2026-09-04. Основание: приложенный артефакт другого агента и текущий код.
Принятые направления реализованы в локальном дереве; существующие изменения
пользователя сохранены. [Схема файлов](idempotency-file-map.md) показывает
текущее устройство. [Руководство по подключению](../src/app/application/idempotency/README.md)
содержит регистрацию policy и границы гарантий.

## Архитектурное решение

Идемпотентность остаётся отдельным application package.
CommandBus маршрутизирует и открывает scope. CommandExecution выбирает владельца
транзакции и обращается к IdempotencyMiddleware. Middleware преобразует команду
и контекст в запрос координатору. Coordinator получает callback, не знает routing
и не зависит от конкретного durable storage.

Вынесение CommandExecution позволяет убрать из bus и состояния идемпотентности,
и SQL-транзакции. Появился один файл с явным выбором транзакционного пути.
Handlers остаются обычными бизнес-обработчиками.

## Что исправлено

| Проблема | Текущий результат |
| --- | --- |
| Общая session могла попасть в параллельные dispatch | build_postgres_command_bus создаёт отдельную session/UoW/dependencies для каждого dispatch |
| Результат локального handler мог принадлежать откатившейся попытке | Возвращается authoritative winner через единый codec |
| Поиск типа результата через Pydantic metadata/MRO | Схема результата и её версия явно регистрируются, TypeAdapter компилируется один раз |
| Неявный scope из полей команды или anonymous | Требуется доверенный CommandContext.idempotency_scope |
| Имя Python-класса определяло namespace | Стабильный operation задаётся при регистрации |
| Регистрации можно менять во время исполнения | Bus замораживает реестр; дубли отклоняются |
| Разные TTL могли продлевать replay за durable retention | Единый expires_at; HOT TTL ограничен оставшимся сроком |
| Истёкшая SQL-запись блокировала новый INSERT | Условный UPSERT заменяет только истёкшую запись |
| Широкий except скрывал ошибки handler/данных | Recovery ограничен потерей durable fence и известным transaction conflict |
| Некорректный DTO мог зафиксироваться вместе с эффектом | Encode и проверка зарегистрированной схемы выполняются до commit |
| Потеря lease / отрицательный CAS игнорировались | HOT_ONLY сообщает ошибку; durable возвращает уже зафиксированный результат |
| Decimal fingerprint зависел от precision | Канонизация сохраняет значимые цифры |
| Циклические импорты через реэкспорты | idempotency/__init__.py оставлен минимальным |

## Три принятых направления

### Отдельные зависимости на каждый dispatch

Новый composition root связывает business repositories, SQL UoW и durable store
одной session. Scope закрывается и при ошибке, и при отмене задачи.
Фабрика dependencies только создаёт объекты; она не выполняет SQL.
Handler не коммитит и не создаёт независимую session.

Для команд без policy и HOT_ONLY бизнес-транзакцией управляет CommandExecution.
Для HOT_DURABLE executor фиксирует бизнес-эффект и replay вместе.
Нельзя считать durable гарантированным только по наличию get/save.

### Явная регистрация команды

Policy задаётся в CommandHandlerRegistry.register:
operation, result_type, result_schema_version, idempotency_policy.
DTO команды не выбирает режим самостоятельно.
Без policy идёт обычное выполнение. Добавление идемпотентной команды требует
регистрации, а не изменения bus/coordinator.

Entrypoint по-прежнему отвечает за транспорт, проверенного caller/права
и передачу key/scope. Авторизация должна действовать и на replay.
Ни клиентский user_id в body, ни hash ключа не заменяют проверку прав.

### Единый deadline

Policy разделяет lease, retention и горячий cache TTL.
Durable result хранит исходный expires_at. Прогрев не начинает retention заново.
На уровне Redis ограничение вычисляется внутри owner-checked Lua; на уровне
SQL lookup/UPSERT учитывают срок, coordinator проверяет snapshot перед ответом.

## Что гарантируется

HOT_ONLY — память в volatile окне. Потеря записи или lease допускает повтор эффекта.
Отказ после выполнения не доказывает, что операция откатилась.

HOT_DURABLE — повтор результата и защита локального commit при общей транзакции.
Конкурирующие callbacks могут запускаться несколько раз, но проигравшие изменения
должны откатиться. Истечение retention разрешает новое выполнение ключа.
Внешние эффекты не входят в SQL rollback.

Coordinator переносим между backend. TransactionalIdempotencyExecution требует
rollback-capable transaction. Для другого storage, включая Cassandra, необходимо
обеспечить DurableExecution в выбранной модели данных; замена одного store
не доказывает эквивалентность гарантий.

## Режим результата отдельного вызова

В `dispatch(..., result_mode=...)` введён ResultMode:
REPLAYABLE возвращает и сохраняет результат; COMPLETION_ONLY проверяет контракт
handler, сохраняет marker без payload и возвращает None. Default — REPLAYABLE.
Режим не зависит от HTTP/Kafka или имени сервиса и не меняет ResultT handler.

Snapshot None и отсутствие сохранённого результата различаются.
REPLAYABLE после completion marker даёт IdempotencyResultNotStoredError;
повторный handler и подстановка текущего состояния ресурса запрещены.
Режим не входит в identity/fingerprint, конкурирующие попытки используют
авторитетную запись победителя.

Для существующей SQL-таблицы подготовлена миграция CHECK constraint:
`001_allow_completion_marker.sql`. Старые snapshot-записи сохраняются;
новая ORM-схема уже принимает marker. Redis namespace остаётся v2.
Миграция автоматически не применяется, readers обновляются до включения marker.

## Что ещё не подключено

- Конкретные handlers/repositories профиля и маршруты HTTP/Kafka: production
  builder готов, но текущий HTTP app публикует только health.
- Запуск на живых PostgreSQL/Redis: нужны DSN и доступные серверы.
- AES-GCM storage decorator: существующий protector не подключён к чтению/записи.
- Миграции между версиями snapshot: текущий codec отклоняет неизвестную версию.
- Периодическая физическая очистка истёкших SQL-записей; логическая expiry уже действует.

Эти пункты не подменяются наличием интерфейсов или unit-тестов.
Для следующего этапа достаточно подключить конкретный command path и прогнать
существующие интеграционные сценарии, затем добавлять capability по реальной потребности.
Разбивать каждое состояние coordinator на отдельный класс сейчас не требуется.

HOT namespace изменён на v2. Записи старой версии не удалены. При наличии
работающих старых workers/записей переход нужно организовать явно; особенно
HOT_ONLY не переносит историю в новый namespace автоматически.

## Проверено

342 unit-теста всего сервиса прошли. Ruff для изменённых Python-файлов —
без замечаний. Четыре PostgreSQL и три Redis интеграционных теста пропущены:
нет тестовых DSN, Docker Engine недоступен. Полный набор HTTP-интеграций не запускался.

Регрессии включают production builder с тестовыми адаптерами, отдельные session
при конкуренции, rollback проигравшего, authoritative replay, отмену задачи,
неверную схему результата до commit, scope isolation, переименование класса,
замороженный registry и прогрев около expiry.
Тесты реальных adapters подготовлены отдельно; unit fakes не подтверждают
серверную семантику SQL-конкуренции или исполнение Redis Lua.
